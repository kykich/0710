# DeepSeek Chat (веб-версия)

Лёгкий веб-чат с языковой моделью **DeepSeek API** на чистой стандартной
библиотеке Python. Ядро (чат, агент, модели, память, стратегии, задачи)
не использует внешних зависимостей; единственная **опциональная** зависимость —
пакет `mcp` для работы с MCP-сервером (см. раздел «MCP» ниже).

Проект — **чисто веб-версия**: встроенный HTTP-сервер открывает страницу в
браузере. Диалог ведётся в окне (в памяти вкладки) и **ничего не сохраняется
на диске** — при закрытии/перезагрузке вкладки чат начинается заново.

## Возможности

- Ввод вопроса в левой колонке, ответ модели — в правой.
- Продолжение диалога: клиент держит историю в памяти окна и отправляет её с
  каждым запросом, поэтому модель «помнит» контекст в рамках текущей вкладки.
- «Новый разговор» очищает диалог локально, в текущем окне.
- Кнопка (клик) в истории запросов слева прокручивает к нужному вопросу.
- Корректный рендер Markdown в ответах (заголовки, списки, таблицы, код).
- Форма работает через **агента** — отдельную сущность, которая инкапсулирует
  всю логику запросов к LLM.
- **RAG (база знаний из PDF)**: локальный поиск по индексированным PDF
  (эмбеддинги Ollama) с УЛУЧШЕННЫМ 2-м этапом — query rewrite, гибридный
  поиск (вектор + слова), порог близости и LLM-реранкер (см.
  `docs/task_rag_rank.md`). Ответ ссылается на источник в скобках
  (`документ#стр.P/chunk.C`), цитаты из источника выделяются жёлтым, а при
  релевантности ниже порога ассистент честно отвечает «не знаю» и просит
  уточнение.

## Требования

- Python 3.9+
- Стандартная библиотека (`urllib`, `json`, `re`, `http.server` и т.п.) —
  для ядра проекта.
- Пакет **`mcp`** — только для MCP-слоя (опционально; без него MCP-функции
  в интерфейсе будут помечены как «недоступны»).

## Установка зависимостей

```bash
pip install -r requirements.txt
```

`requirements.txt` ставит единственный внешний пакет — `mcp` (Model Context
Protocol). Ядро чата работает и без него; установка нужна только для
подключения к MCP-серверу.

## Запуск

```bash
python rtk_web.py
```

На Windows также можно:

```powershell
py rtk_web.py
```

Порт и хост по умолчанию — `127.0.0.1:8000`. Можно указать свой порт (и хост):

```bash
python rtk_web.py 9000           # http://127.0.0.1:9000
python rtk_web.py 9000 0.0.0.0   # доступ с других машин
```

После запуска браузер откроет страницу чата. Если `index.html` открыт как
локальный файл, страница автоматически направит вас на порт запущенного сервера.

## Как это работает (кратко)

1. Страница накапливает диалог в памяти вкладки.
2. При отправке вопроса клиент шлёт `POST /api/ask` с `question` и всей своей
   историей `history[]`.
3. HTTP-сервер передаёт запрос **Агенту** — отдельной сущности, которая сама
   строит сообщения, обращается к моделям через API и собирает ответ.
4. Сервер возвращает клиенту результат агента; ничего не сохраняет.
5. Клиент берёт ответ, кладёт его в историю окна и показывает с рендером
   Markdown.

## Архитектура: агент как отдельная сущность

Вся логика запроса инкапсулирована в классе `rtk_app.agent.Agent`:

- **Приём запроса** — метод `answer(question, history)` принимает вопрос
  пользователя и (при наличии) историю диалога.
- **Инкапсуляция логики** — агент сам формирует список сообщений
  (добавляет системный промпт), вызывает API DeepSeek/GigaChat, измеряет
  время, подсчитывает токены и стоимость, рендерит ответ в HTML и возвращает
  единообразный результат `{ok, html, text, answers, meta}`.
- **Делегирование** — веб-сервер (`web/server.py`) лишь передаёт запрос
  агенту и отдаёт результат клиенту; сам он не знает, какие модели вызываются
  и как обрабатывается ответ.

Один экземпляр агента создаётся при запуске сервера и обслуживает все
запросы пользователей.

## MCP (Model Context Protocol)

Проект умеет работать с инструментами **MCP-сервера**: подключиться к нему,
получить список доступных инструментов (`list_tools`) и вызвать нужный
инструмент (`call_tool`).

- **`yandex_calendar_server.py`** — MCP-сервер **Яндекс.Календаря** (CalDAV):
  `list_calendars`, `list_events`, `find_event`, `create_event`,
  `update_event`, `delete_event`. Учётные данные берутся из файла `ya.txt`
  (первая строка — логин/email, вторая — пароль приложения с доступом к
  календарю; файл в `.gitignore`). Для работы нужен пакет `caldav` (см.
  `requirements.txt`).

  Инструменты работы с событиями умеют искать и адресовать события
  **«по-человечески»**, без UID:
  - `find_event(summary, date, start, end, location)` — найти события по
    части названия («мойка» найдёт «Мойка машины»), дате/периоду и месту;
    удобно уточнить, какое событие имеется в виду.
  - `update_event` / `delete_event` принимают ЛИБО `uid`, ЛИБО
    `find_summary` + `date` (или `summary` + `date`/`start`/`end`/`location`).
    Если под описание подходит **несколько** событий — возвращается их список
    для уточнения (ничего не удаляется/не меняется «наугад»).
  - Для **повторяющихся** событий (RRULE) `delete_event` удаляет **только
    выбранное вхождение** (добавляя EXDATE в правило, не трогая серию), а
    `update_event` правит серию целиком.
  - Поиск по названию без указания дат идёт по широкому окну
    (±`CALENDAR_SEARCH_YEARS` лет, по умолчанию 2) через `cal.search`
    (надёжнее, чем `cal.events()`, который на Яндексе отдаёт не все ресурсы).
- **`currency_server.py`** — MCP-сервер **«Время»**: возвращает время от начала
  текущего дня (00:00:00) до текущего момента и пересчитывает его в другие
  единицы. Значение берётся из локального времени машины (`datetime.now()`),
  внешних зависимостей и сети не требуется:
  - `time_since_midnight()` — время от начала дня в формате `HH:MM:SS`
    с ведущими нулями (например, `09:05:03`);
  - `minutes()` — то же время в формате `MM:SS` (минуты:секунды, например,
    `545:03`);
  - `hours()` — то же время в десятичных часах `HH.HHH` (три знака после точки,
    с округлением; например, `9.084`);
  - `ping()` — проверка живости сервера.

  > ℹ️ Файл сохранён под именем `currency_server.py`, а id сервера в
  > `MCP_SERVERS` — `currency` (совместимость со ссылками композиции task5);
  > валютный функционал полностью удалён.

- **`weather_server.py`** — MCP-сервер **«Погода»** (OpenWeatherMap): текущая
  погода и прогноз по городу. API-ключ берётся из файла `w.txt` (одна строка —
  ключ с https://openweathermap.org; файл в `.gitignore`, внешних зависимостей
  не требуется — используется стандартная библиотека `urllib`):
  - `find_city(city)` — найти город по названию (страна, координаты);
  - `current_weather(city)` — текущая погода (температура, описание, ветер,
    влажность, давление); принимает и координаты `«lat,lon»`;
  - `forecast(city, days)` — прогноз по дням (мин/макс, описание; до 5 суток);
  - `ping()` — проверка живости сервера.
  > ⚠️ OpenWeatherMap активирует новый ключ не мгновенно (до ~2 часов после
  > регистрации). Пока ключ не активен, сервер вернёт понятное сообщение про
  > ошибку 401 — это ответ самого API, а не сбой сервера.

  **Сборщик и хранитель.** Сервер «Погода» накапливает запросы и сохраняет
  их по странам:
  - **сборщик (collector)** — каждая пара «запрос погоды + ответ» (от
    `current_weather`/`forecast`) складывается в накопитель
    `session/weather_collector.json`. Как только накопилось
    **`COLLECT_THRESHOLD` (= 5)** ответов — сборщик **автоматически** передаёт
    их «хранителю» и очищает накопитель;
  - **хранитель (keeper)** — принимает запросы от сборщика, **группирует их
    по КОДУ СТРАНЫ** (RU, DE, FR, …) и пишет **таблицу** в файл `weathe.txt`
    (в `.gitignore`);
  - служебные инструменты: `collector_status` (сколько накоплено),
    `collector_flush` (принудительно передать хранителю, не дожидаясь порога),
    `keeper_report` (показать таблицу `weathe.txt`).

  Общая логика: **запрос погоды → ответ (хранит сборщик) → когда ответов
  становится 5 → передача хранителю.**
- **`zampolit_server.py`** — MCP-сервер **«Замполит»** (композиция task5):
  по времени начала события выбирает ФОРМАТ вывода времени (до полудня —
  минуты, после полудня — часы, событие на весь день — без изменения
  `HH:MM:SS`) и приводит время начала к этому формату:
  `classify_time`, `format_for_event`, `build_pairs(events_json)`, `ping`.
- **`zavhoz_server.py`** — MCP-сервер **«Завхоз»** (композиция task5):
  сохраняет пары «событие + время» в JSON-файл `session/zavhoz.json`:
  `save_pairs`, `load_pairs`, `info`, `clear`.
- **`doska_server.py`** — MCP-сервер **«Доска»** (композиция task5): по запросу
  выводит данные «Завхоза» **таблицей «событие ↔ время»**: `show_board`,
  `show_board_html`.

### Композиция MCP-серверов (см. `docs/task5.md`)

Пять MCP-серверов собираются в **пайплайн**, запускаемый **отдельной кнопкой
«Запустить композицию»** в разделе MCP (затем — фоновым тиком раз в минуту,
пока активен режим композиции):

1. **«календарь»** — события на ближайшие **7 дней** (`COMPOSITION_DAYS_AHEAD`),
   включая события **на весь день** (без времени начала);
2. **«замполит»** — по каждому событию выбирает ФОРМАТ вывода времени по
   времени начала (00:00–12:00 → **минуты** `M:SS`, 12:00–24:00 → **часы**
   `HH.HHH`, весь день → без изменения `HH:MM:SS`) и приводит время начала к
   этому формату;
3. **«завхоз»** — сохраняет результат в `session/zavhoz.json`;
4. **«доска»** — по запросу пользователя в чате выводит данные «Завхоза»
   **таблицей** «событие ↔ время» (в композиции напрямую не участвует,
   читает готовый снимок).

**Уточнения логики:**

- **Композиция и чекбокс «Использовать MCP» — ВЗАИМОИСКЛЮЧАЮЩИЕ.** Композиция
  запускается **отдельной кнопкой** и работает **сама по себе** (фоновый тик).
  При запуске композиции чекбокс «Использовать MCP» **выключается**
  автоматически. Обратно: **включение** чекбокса «Использовать MCP»
  **останавливает композицию** и переводит сервер в режим отдельных
  MCP-серверов по выбору.
- **Запрос при активной композиции обслуживается МОДЕЛЬЮ из селекта
  «Модель MCP»** — через MCP-путь. Выбранная сверху модель/персона при этом
  **не требуются**: запрос не блокируется сообщением «выберите модель или
  создайте персону».
- **MCP-режим включается ТОЛЬКО чекбоксом «Использовать MCP»** (и запросом к
  «Доске»). **Сам выбор сервера в списке** (без чекбокса) MCP-режим НЕ
  включает — иначе после запуска композиции обычные запросы уходили бы
  выбранному серверу. Выбранная сверху модель/персона при этом требуются как
  обычно.
- **Запрос к «Доске» — единственное исключение:** он обрабатывается MCP-путём
  даже при выключенном чекбоксе (с предварительным обновлением данных
  композицией). Выбранная сверху модель и персона при этом **не требуются** —
  запрос не блокируется сообщением «выберите модель или создайте персону».
- **Модель для запроса к «Доске» берётся из селекта «модель MCP»**
  (`mcp_model`), а не из моделей сверху/персоны.
- **После нажатия «Запустить композицию»** в чат выводится **отдельное
  сообщение** со списком задействованных MCP-серверов и кратким описанием
  работы каждого (формируется `_format_composition_message`).
- **Запрос к «Доске»** сначала **обновляет данные до актуального состояния**
  (оркестратор прогоняет пайплайн календарь → замполит → завхоз заново), и
  только затем выводит таблицу.

Оркестратор композиции — `web/server.py` (`_composition_run`): он вызывает
серверы по очереди через `mcp_client` (события календаря передаются
«Замполиту» строкой JSON), а «Доска» читает тот же файл, что записал «Завхоз».
Фоновый **тик** (`COMPOSITION_TICK_SECONDS`, по умолчанию 60 c) прогоняет
пайплайн автоматически — «календарь проверяет каждую минуту состояние событий
на 7 дней вперёд». Настройки — в `rtk_app/config.py` (блок `COMPOSITION_*`,
в т.ч. `COMPOSITION_SERVERS` — состав и описания для сообщения).

### Работа по расписанию (см. `docs/task4.md`)

MCP-серверы умеют работать **по расписанию** — с сохранением данных в JSON и
выдачей агрегированного результата. Фонового демона нет: MCP-сервер
запускается на время вызова, поэтому задания **персистентны** (хранятся в
`session/mcp_jobs.json`) и исполняются **лениво** (при любом обращении к
серверу) либо явным вызовом `run_due()` — так «24/7» эмулируется
персистентностью состояния. Общий механизм заданий — `rtk_app/jobs_store.py`.

- **Календарь — напоминалка до события (с повтором):**
  - `schedule_reminder(uid|summary, date, lead_minutes, repeat_minutes|repeat_hours)`
    — напомнить за `lead_minutes` минут до начала события (по UID ИЛИ по
    названию/дате) и **повторять каждые** `repeat_minutes`/`repeat_hours`
    (например, `repeat_hours=1` — раз в час; `repeat_minutes=1` — раз в
    минуту; `0` — один раз). Повторы идут, **пока не наступит событие**;
  - `list_reminders()`, `cancel_reminder(id)` — список и отмена;
  - `due_reminders()` / `run_due()` — наступившие напоминания (что озвучить).
- **Время — пересчёт времени от начала дня:** сервер «Время»
  (`currency_server.py`) возвращает время от полуночи до текущего момента и
  умеет пересчитать его в другие единицы:
  - `time_since_midnight()` — `HH:MM:SS` (ведущие нули);
  - `minutes()` — `MM:SS` (минуты:секунды);
  - `hours()` — `HH.HHH` (десятичные часы, 3 знака после точки).
- **Выдача сводки — через модель по запросу:** инструменты возвращают текст,
  а модель (агент) пересказывает его пользователю. Данные заданий и точек
  хранятся в `session/mcp_jobs.json` (файл внутри `session/`, в git не попадает).
- **Выбор сервера в интерфейсе.** В левой колонке (блок **MCP**) есть
  выпадающий список «сервер MCP». Доступны шесть серверов — **Яндекс.Календарь**
  (`calendar`), **Время** (`currency`), **Погода** (`weather`),
  **Замполит** (`zampolit`), **Завхоз** (`zavhoz`) и **Доска** (`doska`);
  список задаётся в `rtk_app/config.py` (`MCP_SERVERS`), выбор сохраняется в
  `session/mcp.json`. Рядом — кнопка **«Запустить композицию»** (пайплайн
  календарь → замполит → завхоз, см. выше).
- **`client.py`** — минимальный MCP-клиент: запускает сервер подпроцессом по
  stdio, устанавливает соединение (`initialize`) и печатает список
  инструментов:

  ```bash
  python client.py                    # сервер календаря (по умолчанию)
  python client.py currency_server.py # сервер «Время»
  ```

- **`rtk_app/mcp_client.py`** — синхронная обёртка над MCP SDK
  (`mcp_list_tools`, `mcp_call_tool`, `mcp_status`) для вызова из
  HTTP-сервера и агента.
- **`rtk_app/agent.py`** — ветка `answer_via_mcp()`: модель выбирает
  инструмент и аргументы, сервер их исполняет, результат возвращается как
  ответ.
- **`web/server.py`** — эндпоинт `GET/POST /api/mcp` (состояние, вкл/выкл,
  выбор сервера, проверка статуса сервера).

> Пакет `mcp` — опциональная зависимость: без него веб-сервер проекта
> запускается, а статус MCP в интерфейсе отображается как «недоступен
> (не установлен пакет mcp)».

## Тесты

Автономные проверки (сеть/LLM не требуются) — запускаются из корня проекта:

```bash
python tests/check_context.py          # сжатие контекста
python tests/check_memory.py           # модель памяти
python tests/check_memory_in_request.py# память в запросе к модели
python tests/check_server_context.py   # контекст на стороне сервера
python tests/check_strategies.py       # стратегии (sliding/facts/branch)
python tests/check_auto_compact.py     # авто-сжатие через HTTP
python tests/check_jobs.py             # задания расписания MCP (JSON, агрегат)
python tests/check_reminders.py        # повторяющиеся напоминания календаря
python tests/check_reminder_repeat.py  # напоминание с повтором каждую минуту (сквозной)
python tests/check_composition.py      # композиция MCP (замполит/завхоз/доска)
python tests/check_weather.py          # погода: сборщик -> хранитель (weathe.txt)
python tests/check_rag.py              # базовый RAG (чанки, индекс, промпт)
python tests/check_rag_rank.py          # улучшенный RAG (гибрид/порог/rewrite/реранк)
python tests/check_rag_citations.py     # источник/chunk_id, жёлтые цитаты, «не знаю»
```

Каждый тест печатает `[OK]`/`[FAIL]` по проверкам и строку
`Итог: N OK, M FAIL`, возвращая код выхода `0` при успехе и `1` при провале.
Общая обвязка вывода — `tests/harness.py`.

`tests/test_mem_highlight.py` — ручная проверка (делает реальный запрос к
модели, требует сеть и ключ).
```
