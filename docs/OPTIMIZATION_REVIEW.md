# Обзор возможностей оптимизации проекта

Дата: ревизия кодовой базы веб-чата (DeepSeek + GigaChat).
Объём: ~365 КБ Python + ~109 КБ JS + ~39 КБ CSS.

Отчёт разделён на три уровня приоритета. Для каждой находки указаны файл,
конкретное место и предлагаемое решение.

---

## 0. Найдено и ИСПРАВЛЕНО в рамках ревизии

### 0.1. [ИСПРАВЛЕНО] Реальная ошибка: тесты падали после добавления инвариантов

`tests/check_auto_compact.py` и `tests/check_server_context.py` содержали
`FakeAgent.answer()`, чья сигнатура **не включала новый параметр
`invariants`**, который `web/server.py::_handle_ask` уже передаёт.
Результат — `TypeError: FakeAgent.answer() got an unexpected keyword argument
'invariants'` и провал теста `check_auto_compact`.

Решение: добавлен `invariants=None` в сигнатуры фейковых агентов.
Автотесты снова зелёные. Это был блокирующий дефект: автотесты — это
«страховочная сетка» проекта.

### 0.2. [ИСПРАВЛЕНО] Убрано мёртвое «одноразовое» ветвление

В `_load_legacy_session_locked` вся ветка разбора (≈90 строк) была обёрнута
в `for _once in (0,):` — бессмысленный цикл на одну итерацию, служивший
лишь для отступа. Убран, тело выпрямлено. Поведение идентично, читаемость
выше.

### 0.3. [ИСПРАВЛЕНО] Дедупликация логики сжатия (3 реализации → 1)

`get_compacted_messages()` и `_summary_messages()` дублировали правило
`[summary] + последние keep`. Обе сведены к единому `_apply_summary_over()`
(который уже использует и `get_context_messages`). Правило «нет summary /
keep <= 0 → вернуть как есть» теперь живёт в ОДНОМ месте.

> Проверка после правок: `python -m py_compile` — ок; все автотесты
> (`check_context` 14 OK, `check_memory` все OK,
> `check_memory_in_request` 11 OK, `check_server_context` 7 OK,
> `check_strategies` 30 OK, `check_auto_compact` 10 OK) — без провалов.

## 1. Высокий приоритет (корректность / риск)

### 1.1. Дублирование логики сжатия в `SessionStore` — [ЧАСТИЧНО ИСПРАВЛЕНО]
`session_store.py` содержит несколько мест сборки `[summary] + последние keep`:
- `get_compacted_messages()`
- `_summary_messages()`
- `_apply_summary_over()` — базовый helper

Все три уже сведены к единому `_apply_summary_over(base)` (см. §0.3).

### 1.2. Две ветки записи одного и того же JSON
`_save_profiles_locked()` и `_save_legacy_locked()` формируют ПОЧТИ
идентичные словари (`messages`, `compact`, `memory`, `task_state`, …) и
пишут их в два файла. Это ~50 строк дублирования и двойной I/O на каждый
запрос (а `_save_locked` вызывается после КАЖДОГО действия). Оптимизация:
собрать «плоский снимок активного профиля» одним методом
`_active_snapshot_locked()` и переиспользовать в обоих местах; писать
легаси-файл — опционально (флаг/только при отладке).

### 1.3. Debug-вывод `print(...)` прямо в горячем пути
В `agent.py`/`web/server.py` **42 вызова `print()`** (трассировка `[TRACE]`,
`[MEMORY]`, `[INVARIANT]`, `[COMPACT]`). Они синхронно пишут в stdout при
каждом запросе (а `[TRACE]` — ещё и внутри цикла по моделям). На Windows
консольный I/O медленный и под нагрузкой становится узким местом.
Оптимизация: ввести модуль `rtk_app/logging.py` с уровнем (`DEBUG`/`INFO`)
из переменной окружения и заменить `print` на `log.debug(...)`. Дополнительно
`print(..., flush=True)` форсирует сброс буфера — убрать `flush` для
некритичных сообщений.

### 1.4. `_handle_ask` дублирует «сборку ответа»
Обработчик возвращает в клиента большой список полей
(`compact/strategy/facts/branches/memory/task/invariants/context`), которые
на 90% совпадают с блоком `GET /api/session`. Оптимизация: вынести
`session.full_state()` (один метод), возвращающий все эти поля; вызывать его
и в `/api/session`, и в `/api/ask`. Это устранит риск, что клиент и сессия
разойдутся по набору полей.

## 2. Средний приоритет (производительность / поддерживаемость)

### 2.1. Полная перерисовка потока на каждый ответ (`js/app.js`)
Функция `render()` очищает `streamEl.innerHTML = ""` и заново строит ВСЕ
пузыри истории на каждый запрос. При длинном диалоге это O(N) DOM-узлов
каждый ход и потеря позиции скролла. Оптимизация: домешивать только новые
пузыри (append), а полный рендер оставить для инициализации/переключения
веток/профилей.

### 2.2. `SessionStore` пишет файл на КАЖДОЕ микро-действие
`_save_locked()` вызывается из `set_compact`, `set_strategy`,
`add_memory_usage` (счётчики!), `set_memory_key` и т.д. За один `/api/ask`
происходит 3–5 полных перезаписей JSON на диск (по 2 файла = до 10 записей).
Оптимизация: «грязный» флаг + отложенный сброс (debounce) либо один
финальный `save()` в конце `_handle_ask`. Счётчики `memory_use` можно не
сохранять синхронно.

### 2.3. Дублирование `SYSTEM_PROMPT` и роли «строго JSON»
В `agent.py` многократно повторяется системная инструкция «отвечай строго
JSON» (в `check_invariants`, `advance_task`, `_ask_move`, `update_facts`,
`compact_update`). Оптимизация: константа `STRICT_JSON_SYSTEM` и общий
helper `_chat_json(provider, model, prompt, ...)`, возвращающий
`parse_facts_json`-результат. Это уберёт ~5 копий `try/except + _chat_text`.

### 2.4. `html_report._render_tokens` — большой `if/elif`-каскад
Обработчик LaTeX разросся до ~150 строк каскада `if cmd == ...`. Для
поддерживаемости: словарь «команда → функция-обработчик» (dict dispatch).
Не критично для производительности (формулы редки), но существенно снижает
связанность.

### 2.5. Избыточные пересборки памяти в ответе
`memory_state()` и `get_facts()` строят копии словарей; `_save_profiles_locked`
внутри `_capture_locked` тоже копирует всё. За один запрос состояние памяти
копируется 4–6 раз. Оптимизация: возвращать `dict(...)` только там, где
копия реально нужна наружу; во внутренних вызовах использовать прямые ссылки.

## 3. Низкий приоритет (стиль / гигиена)

### 3.1. `import urllib.parse` / `import subprocess` внутри функций
В `web/server.py` импорты `urllib.parse`, `subprocess`, `sys` сделаны ВНУТРИ
`do_GET`/`do_POST` (выполняются на каждый запрос). Перенести в шапку модуля.

### 3.2. Магические числа
`pause_at=35`, `timeout=60`, лимит `80` при переименовании ветки, `50` в
журнале задачи — вынести в `config.py`.

### 3.3. `_coerce_temperature` / `_coerce_max_tokens` — кандидаты в статику
Оба не используют `self` — сделать `@staticmethod`.

### 3.4. Устаревший код-«шум» — [ЧАСТИЧНО ИСПРАВЛЕНО]
`_facts_message()` помечен как «устаревший», но всё ещё в файле (оставлен
намеренно для обратной совместимости). Трюк `for _once in (0,):` в
`_load_legacy_session_locked` уже убран (см. §0.2).

### 3.5. `rtk_app/__init__.py::__all__` неполон
Перечислены не все модули (нет `session_store`, `task_state`, `key_check`,
`html_report`). Привести `__all__` в соответствие или убрать.

### 3.6. CSS: `.msg.a .variant-*` стили инвариантов добавлены в конец файла
Логически относится к группе «Модели (variant)»; для поддерживаемости
сгруппировать рядом. Косметика.

## 4. Что сделано ХОРОШО (не трогать)

- Чистая архитектура: HTTP-слой делегирует всё `Agent`, а не содержит логики LLM.
- Идемпотентность/потокобезопасность `SessionStore` через `RLock`.
- Тесты офлайн, без сети (`tests/harness.py`) — 113+ проверок.
- Отсутствие внешних зависимостей (только stdlib) — соответствует `requirements.txt`.
- Разделение памяти на три типа с явным выбором слоя (задания A/B1/B2).
