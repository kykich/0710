# Улучшенный поиск RAG (2-й этап: фильтрация/реранкинг + query rewrite)

## Задача

Базовый RAG (1-й этап, `rtk_app/rag.py`) делал простой векторный поиск
`top-k` по косинусной близости эмбеддингов Ollama. На практике этого мало:

* запрос пользователя часто сформулирован «бытовым» языком, а нужный раздел
  документа называется профессиональным термином (например, пользователь
  спрашивает «как сделать обратную засечку», а в документе раздел назван
  «Обратная засечка», «Координатная засечка», «resection»);
* близкие по вектору страницы «общего описания» прибора могут перебивать
  конкретный раздел с процедурой.

Поэтому добавлен **второй этап** обработки результатов поиска.

## Что реализовано

| Возможность | Где | Настройка |
|---|---|---|
| **Query rewrite** — переформулировка запроса в несколько поисковых формулировок силами LLM (синонимы, проф. термины) | `rtk_app/rag_llm.py`, метод `Agent.rewrite_query` | `RAG_REWRITE`, `RAG_REWRITE_COUNT`, `RAG_REWRITE_MODEL` |
| **Гибридный поиск** — к косинусной близости подмешивается лексический сигнал (совпадение ключевых слов запроса) | `rtk_app/rag.py` (`tokenize_ru`, `lexical_score`, `hybrid_score`) | `RAG_HYBRID`, `RAG_HYBRID_ALPHA` |
| **Пул кандидатов** — набираем больше кандидатов ДО фильтрации/реранка | `rtk_app/rag.py` (`_score_rows`, `search_multi`) | `RAG_POOL_MULT` |
| **Фильтрация по порогу** — отсечение кандидатов ниже порога близости | `rtk_app/rag.py` (`search_multi`) | `RAG_MIN_SCORE` |
| **LLM-реранкер** — пересортировка кандидатов по релевантности силами LLM | `rtk_app/rag_llm.py`, метод `Agent.rag_rerank` | `RAG_RERANK`, `RAG_RERANK_MODEL`, `RAG_RERANK_CANDIDATES` |

Все переключатели доступны в интерфейсе (левая колонка, блок «RAG»).

## Архитектура (вариант B)

RagStore (`rtk_app/rag.py`) умышленно НЕ зависит от LLM. Поэтому:

* «чистая» часть (эмбеддинги + лексика + порог + пул + сортировка) живёт
  в `rag.py`;
* LLM-части (query rewrite + LLM-реранкер) вынесены в `rtk_app/rag_llm.py`
  и вызываются из **сервера** (`web/server.py`, `_handle_ask`), который уже
  имеет доступ к агенту и его моделям;
* в `RagStore.build_context` эти LLM-операции передаются как **callback-и**
  (`queries`, `rerank_fn`), поэтому RagStore остаётся тестируемым офлайн.

Поток обработки запроса:

```
вопрос
  │
  ├─ (если rewrite)  Agent.rewrite_query ──► [вопрос, формулировка1, ...]
  │
  ├─ RagStore.search_multi(queries)
  │     ├─ эмбеддинги каждой формулировки (Ollama)
  │     ├─ cosine по всем формулировкам (берём max)
  │     ├─ lexical_score (совпадение ключевых слов)
  │     ├─ hybrid_score = alpha*cosine + (1-alpha)*lexical
  │     ├─ сортировка, пул = top_k * pool_mult
  │     └─ отсечение по min_score ──► top_k кандидатов
  │
  ├─ (если rerank=llm)  Agent.rag_rerank(candidates) ──► пересортировка
  │
  └─ build_context ──► текст RAG → системный промпт модели
```

## Ключевой кейс (регрессионный тест)

В тестовом каталоге документ `otc682.pdf`:

* стр. 10 — общее описание прибора;
* стр. 54 — раздел «Обратная засечка».

Лексический сигнал поднимает страницу 54 над страницей 10, даже если по
чистому косинусу они близки. Это проверяется тестом
`tests/check_rag_rank.py` (раздел 3, «Гибридное ранжирование»).

## Настройки (`rtk_app/config.py`)

```python
RAG_REWRITE = True          # выполнять query rewrite через LLM
RAG_REWRITE_COUNT = 3       # сколько формулировок генерировать
RAG_REWRITE_MODEL = ""      # "" — модель по умолчанию (GigaChat)

RAG_HYBRID = True           # гибридный поиск (косинус + лексика)
RAG_HYBRID_ALPHA = 0.6      # вес косинуса; вес лексики = 1 - alpha

RAG_POOL_MULT = 6           # пул кандидатов = top_k * pool_mult
RAG_MIN_SCORE = 0.0         # порог (0.0 — выключен)

RAG_RERANK = "none"         # "none" | "llm"
RAG_RERANK_MODEL = ""       # "" — модель по умолчанию
RAG_RERANK_CANDIDATES = 12  # сколько кандидатов подавать LLM-реранкеру
RAG_LLM_TIMEOUT = 60        # таймаут LLM-вызовов rewrite/rerank
```

## Ссылки на источник, подсветка цитат и порог «не знаю»

Три требования к КАЧЕСТВУ ответа поверх найденных фрагментов:

### 1. Источник в скобках + section/chunk_id

* `rag.format_citation_id(file, page, chunk)` собирает короткий id вида
  `otc682.pdf#стр.54/chunk.3`;
* заголовок каждого фрагмента в `build_context` содержит этот id
  (`[фрагмент: otc682.pdf, id=otc682.pdf#стр.54/chunk.3]`), а промпт
  (`Agent.rag_system_prompt`) ОБЯЗЫВАЕТ модель подтверждать каждый факт
  ссылкой в круглых скобках: `(otc682.pdf#стр.54/chunk.3)`;
* `rag.format_sources` отдаёт поле `citations`, и блок «Источники» в
  карточке ответа (
  `Agent._render_sources_html`) показывает id в скобках.

### 2. Цитаты из источника — жёлтым

* модель оборачивает дословную цитату в маркеры `[[S]]…[[/S]]`
  (инструктируется в RAG-промпте); `html_report.render_source_marks`
  превращает их в `<span class='src-quote'>` (жёлтый фон);
* запасной детерминированный путь: если модель использовала обычные
  «кавычки-ёлочки», `html_report.highlight_source_quotes` подсветит и их
  (только когда ответ строился с RAG-контекстом; внутри `[[S]]` двойной
  подсветки нет).

### 3. Порог → «не знаю» + просьба уточнить

* если RAG включён, индекс доступен, но ни один фрагмент не прошёл
  `RAG_MIN_SCORE` — сервер (`web/server.py`) выставляет
  `rag_low_relevance=True`;
* `Agent.answer(rag_low_relevance=True)` ДЕТЕРМИНИРОВАННО (без вызова LLM)
  возвращает честный отказ `RAG_LOW_RELEVANCE_TEXT` («Я не знаю …
  уточните вопрос …») — защита от выдумывания фактов.

## Проверка

```
python -m tests.check_rag            # базовый RAG (54 проверки)
python -m tests.check_rag_rank       # 2-й этап: гибрид/порог/rewrite/реранкер (55)
python -m tests.check_rag_citations  # источник/chunk_id, цитаты, «не знаю» (38)
```

Тесты работают ОФЛАЙН (без Ollama): эмбеддинги подменяются детерминированной
фейковой функцией, LLM — фейковым агентом (`_FakeAgent`).
